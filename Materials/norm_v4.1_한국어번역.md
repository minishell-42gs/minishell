# The Norm (42 코딩 표준)

## 버전 4.1

**요약:** 이 문서는 42에서 적용되는 표준(Norm)을 설명합니다. 코드를 작성할 때 따라야 할 규칙들을 정의하는 프로그래밍 표준입니다. Norm은 기본적으로 Common Core 내의 모든 C 프로젝트와, 명시적으로 지정된 프로젝트에 적용됩니다.

---

## I. 서문

**norminette**는 소스 코드의 Norm 준수 여부를 검사하는 Python 기반 오픈소스 코드입니다. Norm의 많은 제약사항을 검사하지만 전부를 검사하지는 않습니다(예: 주관적 제약사항). 캠퍼스의 특별한 지역 규정이 없는 한, 평가 시 검사 항목에 대해서는 **norminette**가 우선합니다. 이하 페이지에서 norminette가 검사하지 않는 규칙은 *(\*)* 표시가 되어 있으며, 코드 리뷰 중 평가자가 발견할 경우 프로젝트 실패(Norm 플래그 사용)로 이어질 수 있습니다.

저장소: https://github.com/42School/norminette

풀 리퀘스트, 제안, 이슈를 환영합니다!

## II. 왜?

Norm은 많은 교육적 필요를 충족하기 위해 신중하게 만들어졌습니다. 아래 모든 선택의 가장 중요한 이유들은 다음과 같습니다:

**순서(Sequencing):** 코딩이란 크고 복잡한 작업을 일련의 기본 명령어들로 분할하는 것을 의미합니다. 이 모든 명령어는 순차적으로 실행됩니다: 하나씩 차례로. 소프트웨어를 처음 만들기 시작하는 초보자는 프로젝트에 대해 단순하고 명확한 구조가 필요하며, 모든 개별 명령어와 실행의 정확한 순서를 완전히 이해해야 합니다. 여러 명령어를 동시에 수행하는 것처럼 보이는 암호화된 언어 구문은 혼란스럽고, 같은 코드 부분에서 여러 작업을 처리하려는 함수는 오류의 원인입니다.

Norm은 각 조각의 고유한 작업이 명확하게 이해되고 검증될 수 있으며, 실행되는 모든 명령어의 순서에 의심의 여지가 없는 단순한 코드 조각을 만들도록 요구합니다. 이것이 함수에 최대 25줄을 요구하는 이유이며, `for`, `do .. while`, 삼항 연산자가 금지되는 이유입니다.

**외관과 느낌(Look and Feel):** 일반적인 동료 학습 과정에서, 또한 동료 평가에서 친구나 동료와 교류할 때, 그들의 코드를 해독하는 데 시간을 쓰고 싶지 않고 코드의 로직에 대해 직접 이야기하고 싶을 것입니다.

Norm은 함수와 변수의 명명, 들여쓰기, 중괄호 규칙, 탭과 공백 등에 대한 지침을 제공하여 특정한 외관과 느낌을 사용하도록 요구합니다. 이를 통해 다른 사람의 코드를 부드럽게 살펴볼 수 있으며 익숙하게 보이고, 코드를 읽는 데 시간을 쓰는 대신 바로 핵심에 도달할 수 있습니다. Norm은 또한 일종의 상표(trademark)입니다. 42 커뮤니티의 일원으로서, 취업 시장에서 다른 42 학생이나 졸업생이 작성한 코드를 알아볼 수 있을 것입니다.

**장기적 비전(Long-term vision):** 이해하기 쉬운 코드를 작성하려는 노력은 유지보수하는 최선의 방법입니다. 다른 사람(자신 포함)이 버그를 수정하거나 새로운 기능을 추가해야 할 때마다, 이전에 올바른 방법으로 했다면 코드가 무엇을 하는지 파악하는 데 귀중한 시간을 잃지 않아도 됩니다. 이는 시간이 많이 걸린다는 이유만으로 코드 유지보수를 중단하는 상황을 방지하며, 시장에서 성공적인 제품을 갖는 것에 대해 이야기할 때 차이를 만들 수 있습니다. 빨리 배울수록 좋습니다.

**참고 자료(References):** Norm에 포함된 일부 또는 모든 규칙이 임의적이라고 생각할 수 있지만, 실제로 무엇을 어떻게 해야 하는지에 대해 생각하고 조사했습니다. 함수가 왜 짧아야 하고 하나의 일만 해야 하는지, 변수 이름이 왜 의미가 있어야 하는지, 줄이 왜 80열을 넘으면 안 되는지, 함수가 왜 많은 매개변수를 받으면 안 되는지, 주석이 왜 유용해야 하는지 등을 구글링해 보길 강력히 권장합니다.

## III. The Norm

### III.1 명명 규칙 (Naming)

- 구조체(structure)의 이름은 `s_`로 시작해야 합니다.
- typedef의 이름은 `t_`로 시작해야 합니다.
- 공용체(union)의 이름은 `u_`로 시작해야 합니다.
- 열거형(enum)의 이름은 `e_`로 시작해야 합니다.
- 전역 변수(global)의 이름은 `g_`로 시작해야 합니다.
- 변수, 함수 이름, 사용자 정의 타입 등의 식별자는 소문자, 숫자, `_`만 포함할 수 있습니다(snake_case). 대문자는 허용되지 않습니다.
- 파일 및 디렉토리 이름은 소문자, 숫자, `_`만 포함할 수 있습니다(snake_case).
- 표준 ASCII 테이블에 속하지 않는 문자는 리터럴 문자열과 char 내부를 제외하고 금지됩니다.
- *(\*)* 모든 식별자(함수, 타입, 변수 등) 이름은 명시적이거나 약어여야 하며, 영어로 읽을 수 있어야 하고, 각 단어는 밑줄로 구분되어야 합니다. 이는 매크로, 파일명, 디렉토리에도 적용됩니다.
- `const`나 `static`으로 표시되지 않은 전역 변수의 사용은 금지되며 norm 오류로 간주됩니다. 프로젝트가 명시적으로 허용하는 경우는 예외입니다.
- 파일은 컴파일되어야 합니다. 컴파일되지 않는 파일은 Norm을 통과할 것으로 기대되지 않습니다.

### III.2 서식 (Formatting)

- 각 함수는 최대 25줄이어야 하며, 함수 자체의 중괄호는 포함하지 않습니다.
- 각 줄은 주석을 포함하여 최대 80열이어야 합니다. 주의: 탭은 단일 열이 아니라 나타내는 공백 수만큼 계산됩니다.
- 함수는 빈 줄로 구분되어야 합니다. 함수 사이에 주석이나 전처리기 지시문을 삽입할 수 있습니다. 최소 하나의 빈 줄이 있어야 합니다.
- 4칸 탭으로 코드를 들여쓰기해야 합니다. 이는 4칸 공백과 같지 않으며, 실제 탭(ASCII 문자 번호 9)을 의미합니다. 코드 편집기가 norminette에 의해 검증될 적절한 들여쓰기를 시각적으로 얻도록 올바르게 설정되어 있는지 확인하세요.
- 중괄호 내의 블록은 들여쓰기되어야 합니다. 중괄호는 struct, enum, union 선언을 제외하고 자체 줄에 단독으로 위치합니다.
- 빈 줄은 비어있어야 합니다: 공백이나 탭이 없어야 합니다.
- 줄은 공백이나 탭으로 끝날 수 없습니다.
- 연속된 빈 줄 두 개를 가질 수 없습니다. 연속된 공백 두 개를 가질 수 없습니다.
- 선언은 함수의 시작 부분에 있어야 합니다.
- 모든 변수 이름은 해당 스코프에서 동일한 열에 들여쓰기되어야 합니다. 참고: 타입은 포함하는 블록에 의해 이미 들여쓰기됩니다.
- 포인터와 함께 사용되는 별표(*)는 변수 이름에 붙어야 합니다.
- 한 줄에 하나의 변수 선언만 가능합니다.
- 전역 변수(허용된 경우), 정적 변수, 상수를 제외하고 선언과 초기화를 같은 줄에 할 수 없습니다.
- 함수 내에서 변수 선언과 함수의 나머지 부분 사이에 빈 줄을 넣어야 합니다. 함수 내에서 다른 빈 줄은 허용되지 않습니다.
- 한 줄에 하나의 명령문 또는 제어 구조만 허용됩니다. 예: 제어 구조 내의 대입은 금지, 같은 줄에 두 개 이상의 대입은 금지, 제어 구조 끝에 개행이 필요 등.
- 필요할 때 명령문이나 제어 구조를 여러 줄로 나눌 수 있습니다. 생성된 다음 줄들은 첫 번째 줄에 비해 들여쓰기되어야 하며, 자연스러운 위치에서 줄을 자르고, 해당되는 경우 연산자는 이전 줄의 끝이 아닌 새 줄의 시작 부분에 위치해야 합니다.
- 줄의 끝이 아닌 한, 각 쉼표나 세미콜론 뒤에 공백이 와야 합니다.
- 각 연산자 또는 피연산자는 하나의 - 그리고 오직 하나의 - 공백으로 구분되어야 합니다.
- 각 C 키워드 뒤에는 공백이 와야 합니다. 단, 타입 키워드(int, char, float 등)와 sizeof는 예외입니다.
- 제어 구조(if, while 등)는 단일 줄의 단일 명령문을 포함하지 않는 한 중괄호를 사용해야 합니다.

**일반 예시:**

```c
int                 g_global;
typedef struct      s_struct
{
    char            *my_string;
    int             i;
}                   t_struct;
struct              s_other_struct;

int     main(void)
{
    int     i;
    char    c;

    return (i);
}
```

### III.3 함수 (Functions)

- 함수는 최대 4개의 명명된 매개변수를 가질 수 있습니다.
- 인수를 받지 않는 함수는 인수로 "void"를 명시적으로 프로토타입에 작성해야 합니다.
- 함수 프로토타입의 매개변수에는 이름이 있어야 합니다.
- 함수당 5개를 초과하는 변수를 선언할 수 없습니다.
- 함수의 반환값은 괄호 사이에 있어야 합니다. 단, 함수가 아무것도 반환하지 않는 경우는 예외입니다.
- 각 함수는 반환 타입과 이름 사이에 하나의 탭이 있어야 합니다.

```c
int	my_func(int arg1, char arg2, char *arg3)
{
    return (my_val);
}

int	func2(void)
{
    return ;
}
```

### III.4 Typedef, struct, enum, union

- 다른 C 키워드와 마찬가지로, struct 선언 시 "struct"와 이름 사이에 공백을 추가합니다. enum과 union에도 동일하게 적용됩니다.
- struct 타입의 변수를 선언할 때, 변수 이름에 일반적인 들여쓰기를 적용합니다. enum과 union에도 동일하게 적용됩니다.
- struct, enum, union의 중괄호 내부에서는 다른 블록과 마찬가지로 일반 들여쓰기 규칙이 적용됩니다.
- 다른 C 키워드와 마찬가지로, "typedef" 뒤에 공백을 추가하고, 새로 정의된 이름에 일반 들여쓰기를 적용합니다.
- 모든 구조체의 이름은 해당 스코프에서 동일한 열에 들여쓰기되어야 합니다.
- .c 파일에서 구조체를 선언할 수 없습니다.

### III.5 헤더 - 일명 include 파일

- *(\*)* 헤더 파일에 허용되는 요소: 헤더 포함(시스템 또는 아닌 것), 선언, define, 프로토타입, 매크로.
- 모든 include는 파일의 시작 부분에 있어야 합니다.
- 헤더 파일이나 다른 C 파일에 C 파일을 포함할 수 없습니다.
- 헤더 파일은 이중 포함으로부터 보호되어야 합니다. 파일이 `ft_foo.h`이면, 보호 매크로는 `FT_FOO_H`입니다.
- *(\*)* 사용하지 않는 헤더의 포함은 금지됩니다.
- 헤더 포함은 .c 파일과 .h 파일 자체에서 주석을 사용하여 정당화할 수 있습니다.

```c
#ifndef FT_HEADER_H
# define FT_HEADER_H
# include <stdlib.h>
# include <stdio.h>
# define FOO "bar"

int     g_variable;
struct  s_struct;

#endif
```

### III.6 42 헤더 - 일명 스타일리시하게 파일 시작하기

- 모든 .c 및 .h 파일은 표준 42 헤더로 즉시 시작해야 합니다: 유용한 정보를 포함하는 특별한 형식의 여러 줄 주석입니다. 표준 헤더는 클러스터의 컴퓨터에서 다양한 텍스트 편집기용으로 자연스럽게 사용할 수 있습니다(emacs: `C-c C-h` 사용, vim: `:Stdheader` 또는 `F1` 사용 등).
- *(\*)* 42 헤더에는 생성자(로그인과 학생 이메일(@student.campus)), 생성 날짜, 마지막 업데이트의 로그인과 날짜를 포함하여 최신 정보가 포함되어야 합니다. 파일이 디스크에 저장될 때마다 정보가 자동으로 업데이트되어야 합니다.

> 기본 표준 헤더가 자동으로 개인 정보로 설정되지 않을 수 있습니다. 이전 규칙을 따르기 위해 변경해야 할 수 있습니다.

### III.7 매크로와 전처리기 (Macros and Pre-processors)

- *(\*)* 생성하는 전처리기 상수(또는 #define)는 리터럴 및 상수 값에만 사용해야 합니다.
- *(\*)* norm을 우회하거나 코드를 난독화하기 위해 생성된 모든 #define은 금지됩니다.
- *(\*)* 표준 라이브러리에서 사용할 수 있는 매크로는 해당 프로젝트의 범위에서 허용된 경우에만 사용할 수 있습니다.
- 여러 줄 매크로는 금지됩니다.
- 매크로 이름은 모두 대문자여야 합니다.
- #if, #ifdef, #ifndef 블록 내에서 전처리기 지시문을 들여쓰기해야 합니다.
- 전역 스코프 외부에서의 전처리기 지시문은 금지됩니다.

### III.8 금지 사항! (Forbidden stuff!)

다음을 사용할 수 없습니다:
- `for`
- `do...while`
- `switch`
- `case`
- `goto`

또한 금지:
- `?`와 같은 삼항 연산자
- VLA (가변 길이 배열, Variable Length Arrays)
- 변수 선언에서의 암시적 타입

```c
int	main(int argc, char **argv)
{
    int     i;
    char    str[argc]; // 이것은 VLA
    i = argc > 5 ? 0 : 1 // 삼항 연산자
}
```

### III.9 주석 (Comments)

- 주석은 함수 본문 안에 있을 수 없습니다. 주석은 줄의 끝이나 자체 줄에 있어야 합니다.
- *(\*)* 주석은 영어로 작성되어야 하며, 유용해야 합니다.
- *(\*)* 주석은 만능(carryall) 함수나 나쁜 함수의 생성을 정당화할 수 없습니다.

> 만능 또는 나쁜 함수는 보통 f1, f2... 같은 명시적이지 않은 함수 이름과 a, b, c... 같은 변수 이름을 동반합니다. 유일한 목적이 norm을 회피하는 것이고 고유한 논리적 목적이 없는 함수도 나쁜 함수로 간주됩니다. 각각 명확하고 간단한 작업을 수행하는 명확하고 읽기 쉬운 함수를 갖는 것이 바람직합니다. 원라이너(one-liner) 등의 코드 난독화 기법을 피하세요.

### III.10 파일 (Files)

- .c 파일에 .c 파일을 포함할 수 없습니다.
- .c 파일에 5개를 초과하는 함수 정의를 가질 수 없습니다.

### III.11 Makefile

Makefile은 norminette에 의해 검사되지 않으며, 평가 가이드라인에 의해 요청될 때 평가 중 학생이 검사해야 합니다. 특별한 지시가 없는 한, 다음 규칙이 Makefile에 적용됩니다:

- `$(NAME)`, `clean`, `fclean`, `re`, `all` 규칙은 필수입니다. `all` 규칙은 기본 규칙이어야 하며 `make`만 입력했을 때 실행되어야 합니다.
- makefile이 불필요하게 재링크(relink)하면, 프로젝트는 비기능적(non-functional)으로 간주됩니다.
- 다중 바이너리 프로젝트의 경우, 위 규칙에 추가로 각 바이너리에 대한 규칙이 있어야 합니다(예: `$(NAME_1)`, `$(NAME_2)`, ...). "all" 규칙은 각 바이너리 규칙을 사용하여 모든 바이너리를 컴파일합니다.
- 소스 코드와 함께 존재하는 비시스템 라이브러리(예: libft)의 함수를 호출하는 프로젝트의 경우, makefile이 이 라이브러리를 자동으로 컴파일해야 합니다.
- 프로젝트를 컴파일하는 데 필요한 모든 소스 파일은 Makefile에 명시적으로 이름이 지정되어야 합니다. 예: `*.c`, `*.o` 등은 사용 불가.
